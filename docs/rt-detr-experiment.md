# RT-DETR 실험 결과

**브랜치**: `experiment/rt-detr`
**목적**: CLAUDE.md 3-1 "RT-DETR도 비교 후보로 고려 가능"에 따른 검증 — YOLO-OBB 대비 비교용 실험.

**결론**: 50 epoch로 예약했었지만, epoch 10에서 의도적으로 중단하고(`--epochs 50`이었으나 조기 종료) 그 체크포인트로 테스트까지 마쳤다. 아래는 그 최종 기록.

---

## 실험 설정

| 항목 | 값 |
|---|---|
| 모델 | `rtdetr-l.pt` (ultralytics) |
| 데이터 | ICONIC 500장, 5클래스 (볼트_주황/볼트_노랑/나무_5구멍/나무_3구멍/나무_2구멍) |
| 라벨 형식 | **AABB** — 원본은 OBB인데 RT-DETR이 OBB를 지원하지 않아 4꼭짓점 min/max로 변환 (`prepare_rtdetr_dataset.py`) |
| Train / Val | 425장 / 75장 (val 15%, seed 42) — CLAUDE.md의 "Train/Test" 방침에서 Test에 해당 |
| 하이퍼파라미터 | epochs=50(예약), batch=8, imgsz=640 → **실제로는 epoch 10에서 중단** |
| 하드웨어 | RTX 4050 Laptop GPU (6GB VRAM) |
| 학습 스크립트 | `src/detection/rt-detr/train_rtdetr.py` |

## 알려진 제약

- AABB로 변환했기 때문에, 회전된 부품(특히 45°/135° 각도로 놓인 나무 막대)은 박스가 실제보다 헐겁게 잡힘 — YOLO-OBB 대비 불리한 조건에서 비교하는 실험.
- val 75장은 소량이라 mAP 수치가 epoch마다 변동이 큼(노이즈 있음).

## 실제 추론 테스트 (epoch 10 체크포인트, `last.pt`)

val 지표(precision/recall/mAP)는 높게 나왔지만, 클래스당 1장씩 5장을 직접 추론해서 눈으로 확인했다.

| 나무_3구멍 | ✅ 정답 감지(conf 0.86), **단 나무_2구멍으로도 동시에 오탐지(conf 0.48)** — 같은 박스 좌표에 클래스 혼동 |

**해석**: val 지표(mAP50 0.99)만 보면 문제없어 보이지만, 실제 추론에서는 클래스 혼동이 남아있었다 — val 셋이 75장으로 작아서 이런 미세한 문제를 못 잡아낸 것으로 보인다. epoch을 늘리면(원래 예약했던 50까지) 개선될 가능성이 높으나, 이번 실험은 epoch 10에서 의도적으로 멈췄으므로 확인은 못 함.

# 2차 실험: 통합 데이터셋 (iconic + assembled_labeled)

**목적**: 1차 실험에서 발견된 나무_2구멍/나무_3구멍 클래스 혼동 문제를, 조립체(여러 부품이 한 프레임에 섞인) 사진을 추가 학습시키면 해결되는지 확인.

## 데이터

| 소스 | 내용 | 장수 |
|---|---|---|
| `data/iconic/` | 부품 1개짜리 ICONIC 사진, OBB→AABB 변환 | 559장 (bolt_1 130, bolt_2 129, mother_part 100, part_2hole 100, part_3hole 100) |
| `data/assembled_labeled/` | 조립체 사진, 이미 AABB, 사람이 직접 라벨링 | 100장 (Model A 20, Model B 40, Model C 40) |
| **합계** | | **659장** |

Train/Val(=Test) 분할은 **소스별·클래스(모델)별로 각각 15%씩** — 전체를 한 덩어리로 섞어서 나누면 소수 그룹(Model A 20장 등) 비율이 틀어질 수 있어서, iconic은 클래스별로 / assembled_labeled는 `model_a/b/c` 파일명 접두사 기준으로 각각 나눔. train 560장 / val 99장.

스크립트: `src/detection/rt-detr/prepare_rtdetr_dataset.py` (두 소스를 합치도록 확장), 출력: `datasets/rtdetr_combined/`

## 하이퍼파라미터

epochs=10, batch=8, imgsz=640, 모델 `rtdetr-l.pt`. 1차 실험과 같은 조건(epoch 10)으로 맞춰서 비교 가능하게 함.

## 실제 추론 테스트 — 클래스 혼동 문제 해결 확인

클래스별 단일 부품 5장 + 조립체(Model A/B/C) 3장, 총 8장을 직접 추론.

### 발견한 문제 — `model_b_029` 중복 검출

기대 5개(mother_part×1, part_2hole×2, bolt_1×2)인데 7개가 나왔다. 좌표를 직접 찍어보니:

- `part_2hole` conf 0.955 @ `[527.6, 98.3, 817.0, 265.3]`
- `part_2hole` conf 0.929 @ `[529.1, 98.5, 816.3, 264.9]` ← 위와 거의 동일 좌표 (중복)
- `mother_part` conf 0.910 @ `[527.8, 108.1, 799.4, 679.2]`
- `mother_part` conf 0.854 @ `[528.8, 106.7, 798.5, 680.1]` ← 역시 거의 동일 좌표 (중복)
- `bolt_1` × 2 (정상, 서로 다른 위치)

1차 실험 때의 "**다른** 클래스가 같은 박스에 동시 검출"과는 다른 종류다 — 이번엔 **같은** 클래스가 소수점 수준으로만 다른 좌표에 중복 검출됐다. RT-DETR은 query 기반이라 원래 NMS 없이도 중복을 억제하도록 학습되는데, epoch 10만 돌려서 이 중복 억제가 아직 덜 수렴한 것으로 보인다. 99장 중 이 1장에서만 발생 — 이례적이지 결정적 문제는 아님.

# 3차 실험: 전체 데이터 통합 (iconic + assembled_labeled + labeled_data_merged)

**목적**: `data/labeled_data`(픽킹 영상 손 포함 프레임 + 조립 진행중 프레임)까지 전부 합쳐서, 더 다양한 상황(손 occlusion, 조립 중간 단계)을 학습에 포함시키면 더 개선되는지 확인.

## 데이터

| 소스 | 내용 | 장수 |
|---|---|---|
| `data/iconic/` | 부품 1개짜리 ICONIC 사진 | 559장 |
| `data/assembled_labeled/` | 완성 조립체(Model A/B/C) 사진 | 100장 |
| `data/labeled_data_merged/` | 픽킹 영상(손 포함) + 조립 진행중 프레임, canonical 클래스로 재매핑 | 321장 (md5 중복 100장 자동 제외) |
| **합계** | | **980장** |

`data/labeled_data`는 클래스 ID 체계가 프로젝트 canonical 매핑과 반대로 돼있던 걸(`merge_labeled_data.py`) 재매핑했고, `data/labeled_data`의 구 `train` 폴더 중 100장은 `data/qwer`/`data/assembled_labeled`와 완전히 동일한 원본이라 md5 해시로 자동 중복 제거했다 (`prepare_rtdetr_dataset.py`).

데이터셋은 `data/aabb/`(AABB, RT-DETR 학습용)와 `data/obb/`(OBB, 메인 YOLO 파이프라인용)로 동시에 만들었고 — 둘 다 같은 seed로 나눠서 train 831장 / test 149장으로 동일하게 분할됨. RT-DETR은 OBB를 지원하지 않으므로 `data/aabb`로 학습.
